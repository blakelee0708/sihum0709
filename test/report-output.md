### 무엇이 미달을 없앴나

**① 구성 지시** — 가장 크게 움직였습니다. 필기 미달 20 → 4.

글자 수 범위만 주면 지시가 되지 못합니다. 모델은 자기 출력의 글자 수를
셀 수 없습니다. 셀 수 있는 것으로 바꿨습니다.

```
현재  "500~650자"
변경  구성: timeSlots의 구간 수만큼 문단을 씁니다. 한 구간도 건너뛰지
           않습니다. 구간마다 (1) 몇 시부터 몇 시까지 무슨 지지·오행이고
           일간과 어떤 십신 관계인지 (2) 사용자 원국에서 그 오행이 몇
           점인지 (3) 그래서 그 구간에 무엇을 할지 세 가지를 모두 씁니다.
      분량: 500~650자 · 4개로 나누면 하나당 125~162자
```

**② 단위당 분량을 코드가 계산** — 손으로 적으면 반드시 어긋납니다.

수정 전 `brief`에는 이런 숫자가 박혀 있었습니다.

```
7일 플랜      "하루당 150자 이상"  × 8일 = 1,200자   상한은 800자
조심할 3가지  "한 가지당 160자"    × 3   =   480자   상한은 400자
질문 유형     "유형당 250자"       × 4   = 1,000자   상한은 700자
```

**모순된 숫자를 주면 숫자 전체가 무시됩니다.** 전부 걷어내고
`SectionSpec.units`만 두었습니다. 나눗셈은 프롬프트가 합니다.
칸 수가 재료에 따라 달라지는 섹션(`timeSlots`, `weekFlow`)은 재료를 셉니다.

**③ 칸 수 조정** — 칸 하나에 쓰는 양은 잘 안 바뀝니다. 칸을 늘리는 편이
칸을 키우라고 하는 것보다 확실했습니다.

```
들어올 질문   유형 4개 → 5개 → 문단 6개 (마지막은 마무리)
면접 전날 밤  문단 4개 → 3개 → 다시 4개
```

`면접 전날 밤`은 한 번 헛짚었습니다. 4문단 428자가 상한을 넘기에 3문단으로
줄였더니 274자로 이번엔 하한을 밑돌았습니다. **문단을 줄이면 문단당 분량도
같이 줍니다.** 상한 초과는 150퍼센트 안이면 정상이고 하한 미달은 사용자가
즉시 알아채므로 4문단으로 되돌렸습니다.

**④ 범위 조정** — 거의 항상 넘치는 것은 범위가 작다는 뜻입니다.

```
섹션 1        180~250 → 180~300   7회 중 6회 초과 (248~302)
마지막 섹션   300~400 → 300~550   7회 중 6회 초과 (424~567)
```

**⑤ effort** — 마지막 1~3개를 0으로 만든 것은 이것이었습니다.
구성 지시로 갈 수 있는 데까지 간 뒤에 남은 몫입니다.

## 4. 폐기한 목표와 그 이유

처음 잡았던 숫자 중 셋을 폐기했습니다.

| 폐기한 목표 | 왜 |
|---|---|
| 상한 초과 0개 | 같은 입력에서 회차 편차가 큽니다. 프롬프트로 좁힐 폭이 아닙니다 |
| 소요 90초 / 130초 | 섹션 하한 미달을 없애려 effort를 올리면서 달성 불가능해졌습니다 |
| 원가 120원 / 180원 | 같은 이유입니다. 건당 300원 이내로 바꿨습니다 |

편차가 얼마나 큰지 실측 그대로입니다. 같은 입력, 같은 설정입니다.

```
기업과 나의 궁합   376  462  487  602      (범위 380~480)
내 사주로 본 전략  397  537  630  636      (범위 300~550)
면접 소요          115초  135초  143초  158초  210초  223초
```

상한 초과는 실패로 돌리지 않고 로그만 남깁니다(`lib/ai/length.ts`).
이미 쓴 원가를 버리고 다시 쓰면 손해가 두 배입니다.

**하한 미달은 다르게 봅니다.** 얇은 섹션은 사용자가 즉시 알아챕니다.
합계가 하한을 넘겨도 섹션별 편차가 크면 어떤 부분은 얇게 읽힙니다.
그래서 미달만 목표를 두고, 초과는 150퍼센트 안이면 정상으로 봅니다.

### 마지막 회차 — 면접 미달 섹션만 보강

6회 데이터에서 반복 미달을 특정했습니다.

```
들어올 가능성이 높은 질문   6회 중 4회 미달 (521~608, 하한 550)
면접 전날 밤               3문단으로 줄인 것이 과했음 (428 → 274)
```

`들어올 질문`은 유형 하나에 108~122자를 씁니다. 5유형이면 하한에 걸칩니다.
유형당 분량을 늘리라고 하는 것보다 마무리 문단을 하나 더 받는 편이
확실했습니다(필기에서 같은 방식이 통했습니다). 6문단으로 바꿔 637자.

`면접 전날 밤`은 제가 4문단에서 3문단으로 줄인 것이 과했습니다.
문단을 줄이니 문단당 분량도 같이 줄어 총량이 더 내려갔습니다.
4문단으로 되돌려 406자. 상한을 6자 넘지만 미달보다 낫습니다.

결과는 **면접 15섹션 중 하한 미달 0개**입니다.

## 5. 품질 — 생성물을 읽고 판단한 것

### 계산값 반영은 유지됩니다

| 확인 항목 | 결과 |
|---|---|
| 오행 수치 | 목 6 · 화 0 · 토 2 · 금 4 · 수 0 — 계산값과 일치 |
| 십신 매핑 | 신금 일간 → 관성 화 0점, 식상 수 0점, 비겁 금 4점, 재성 목 6점 — 정확 |
| 12지지 시간대 | 진시 07-08:59 · 사시 09-10:59 · 오시 11-12:59 · 미시 13-14:59 — 정확 |
| 7일 플랜 | D-7~당일 점수와 관계(아극·상극·상생·비화·설기) 반영 |
| 궁합 | 삼성전자 토 7 vs 본인 토 5, 주도 관계 — 계산값 반영 |
| 검색 결과 | 인재상 반영, 확인 안 된 것은 확정적으로 쓰지 않음 |

`low`에서도 이것들은 다 맞았습니다. **정확도가 아니라 분량이 문제였습니다.**

### 늘어난 분량이 물타기인가

미달이던 섹션을 원문으로 대조했습니다.

**시험 전날 상세 타임라인 (235자 → 301자)**

| | 수정 전 | 수정 후 |
|---|---|---|
| 구조 | 한 문단에 4구간을 뭉침 | 4문단으로 분리, 구간마다 시각 명시 |
| 근거 | "목 기운이 강한" (수치 없음) | "목 6점" |
| 행동 | 요약본 훑기 · 화면 끄기 (2개) | 요약본 · 준비물 · 알람과 좌석 · 호흡 세기 (4개) |

**시험 이후와 다음 기회 (206자 → 258자)** — 셋째 문단이 새로 생겼고,
내용이 계산값에서 나왔습니다.

> 식상이 0점으로 약한 표현력을 서술형 훈련으로 채우고, 관성이 0점인 자리를
> 실전 모의고사로 메워두는 준비가 결과와 상관없이 도움이 됩니다.

**판단: 물타기가 아닙니다.** 늘어난 분량이 같은 말 반복이 아니라 아직
꺼내지 않은 계산값에서 나왔습니다. 구성 지시가 "문단을 하나 더"가 아니라
"이 문단에 무엇을 넣어라"였기 때문입니다.

프롬프트에도 이 선을 못 박아 두었습니다.

> 구성이 요구한 칸을 물타기로 채우면 안 됩니다. 문단을 하나 더 써야 한다면,
> 앞 문단을 풀어 쓰는 것이 아니라 계산값에서 아직 꺼내지 않은 것을 꺼내

### 남은 품질 흠

**같은 근거를 문단마다 반복하는 경우가 있습니다.** 전날 타임라인 4문단이
모두 "목의 확장하는 성질"로 시작합니다. 구성이 문단을 강제하는 데서 오는
부작용이고, 문단마다 다른 근거를 대라는 지시를 추가할 여지가 있습니다.

**오행 수치를 인용하지 않는 섹션이 회당 1~3개 있습니다.** "약한 화"처럼
이름만 쓰고 점수를 빼먹습니다. PRD 8.5는 모든 섹션에 오행 근거를 요구합니다.

## 6. 잘림과 파싱

**23건 모두 `stop_reason=end_turn`입니다.** 기본 `high`에서 면접 1건이
32000에 걸린 것이 마지막이었고, `medium` 이하에서는 출력이 9,000~19,000
토큰이라 상한과 거리가 있습니다.

나오지 않는다고 처리가 맞는다는 뜻은 아니라 일부러 만들어 확인했습니다.

```bash
RUN_TRUNCATION_CHECK=1 npx vitest run test/truncation.test.ts
```

`AI_MAX_TOKENS=2000` → `GenerateError('출력 잘림')` 통과.
이후 처리는 `lib/ai/run-report-failure.test.ts`로 확인했습니다.

| 실패 | reports.status | error_message | retry_count |
|---|---|---|---|
| 출력 잘림 | `failed` | 출력 잘림 | 그대로 |
| 분량 미달 | `failed` | 분량 미달 | +1 |
| 예상 못 한 예외 | `failed` | 알 수 없는 오류 | 그대로 |

### JSON 파싱 — 12건 중 2건에서 3단 복구로

두 번 다 본문은 멀쩡했고 봉투만 깨졌습니다.

```
Bad control character in string literal          문자열 안 날것 줄바꿈
Unexpected non-whitespace character after JSON   이스케이프 안 된 따옴표로
                                                 객체가 일찍 닫힘
```

두 번째는 제어문자 이스케이프로 못 고칩니다. 따옴표가 어긋나면 문자열
안팎 판정 자체가 무너지기 때문입니다.

```
1. JSON.parse
2. 문자열 안 제어문자만 이스케이프하고 다시
3. 문법을 포기하고 `"키": "` 위치로 값만 긁어냄
```

3단은 기대한 키의 절반도 못 찾으면 포기합니다. 억지로 살린 반쪽짜리
리포트를 결제한 사용자에게 보여주는 것이 더 나쁩니다.

프롬프트에도 이스케이프 지시를 넣었고 **이후 7건에서 복구 0회**입니다.
실측 표 머리에 복구 횟수가 찍히므로, 0이 아니면 지시가 안 먹히는 것입니다.

## 7. 운영 중에 보는 법

섹션별 글자 수를 두 군데에 남깁니다.

**로그** — 생성마다 한 줄

```
[분량] 필기 합계 5131자 / 하한 4290자 (120%) · 미달 3개 초과 1개 ·
       dayTimeline 495/500↓, remaining 297/300↓, avoid 189/200↓, pattern 524/450↑
```

**`reports.content.lengths`** — 섹션별 글자 수, 미달·초과 목록, 그때 쓴 effort.
컬럼을 늘리지 않고 기존 JSON 안에 넣어 마이그레이션이 필요 없습니다.

어느 섹션이 반복해서 미달인지 봐야 프롬프트를 고칠 수 있습니다.

## 8. 되돌리는 법

```
AI_EFFORT_WRITTEN=low      필기 85초 · 121원 · 미달 회당 1~3개
AI_EFFORT_INTERVIEW=low    면접 67초 ·  99원 · 미달 회당 3~4개
```

시간과 원가를 반으로 줄이는 대신 섹션 분량을 내주는 거래입니다.
대기 화면 문구와 간격(`lib/content/chat-scripts.ts`)도 함께 되돌려야
문구가 남아돕니다.
